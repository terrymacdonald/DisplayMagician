# DisplayMagician.ControlService

This project hosts the machine-wide Windows service named **DisplayMagician Control Service**. It authenticates local clients, routes requests to the correct per-user User Agent, serialises machine display operations, retains operation status and pending decisions, coordinates persistence/recovery, and owns machine-level scheduling, audit, diagnostics, and the local integration foundation.

It does not show UI, launch games, inspect Steam or desktop windows, or change display/audio settings directly. Those interactive-session responsibilities belong to `DisplayMagician.UserAgent`. It owns approved remote-device grants and credential hashes, ten-minute pairing sessions, host/TLS identity state, and the Gateway's HTTP idempotency ledger. Completed responses are retained for 24 hours; interrupted reservations remain blocked and return an outcome-unknown result. Local and paired-client approval grant exactly the candidate-requested capabilities. `DisplayMagician.Gateway` is the only network-facing adapter and asks the service to enforce these rules.

Active shortcut window-placement queries, snapshot requests, and clear requests are routed to the current user's Agent. The service never enumerates or moves windows. Save and clear requests use the normal mutating-request replay protection.

The Gateway replay ledger uses the shared atomic JSON writer and retains its backup. If the ledger cannot be loaded or contains invalid records, ControlService still starts and local functionality remains available, while remote mutations requiring replay protection are rejected. Existing files are preserved for repair; an older backup is never silently substituted because it could forget an already executed command. Repair the authoritative ledger and restart ControlService to re-enable those mutations.

When an authorised interactive user session has no connected Agent, the service can request `DisplayMagician.SessionLauncher` to demand-start one in that verified SID/session. A physical-console session is not required. QR pairing records that local SID/session as the paired device's preferred route. ControlService revalidates it before every remote request, falls back only when the owner has exactly one healthy ready Agent, and otherwise requires an explicit target selection.

Both launch and stop commands carry the shared Hello/Welcome handshake over the SessionLauncher pipe. The common caller validates response version, message type, request ID, endpoint kind, and required capabilities. Caller and broker must be deployed together; this adds metadata to the shared result without changing the version-1 pipe or persisted configuration schemas.

Control Service routes work only to a ready Agent whose process and command-pipe identity match the fixed installed payload. It bounds pipe handshakes and subscribers, retains successful mutating client responses for 24 hours for safe retry, and makes lagging event subscribers reconnect for an authoritative status/decision snapshot. Active operation statuses remain available; terminal statuses are retained for seven days or the newest 100 per user, whichever bound is reached first. It journals operation, decision, and saved-resource changes for the planned Gateway SSE replay path, bounded per user to 24 hours, 10,000 events, and 10 MiB. The Gateway-only pipe reads bounded replay batches after checking the caller's grants and preferred session. Bulk repository edits require a readable pre-edit snapshot so creation, update, and deletion events have accurate saved IDs.

An authorised session requesting display control takes over an idle lease from another session, including when the previous Agent is still heartbeating. Active operations and recovery-required leases remain reserved for their owner until the work or recovery is resolved.

Saved-resource mutations write a durable pending-publication marker before reaching UserAgent. Successful event publication clears it; an interrupted or failed publication retires that user's old replay cursors and forces a fresh snapshot. Startup also reconciles persisted operation/decision state against journal records so a crash between state commit and its event callback cannot silently leave a replay gap. Replay boundaries remain usable when all retained events have expired or exceeded the item/byte limits.

Every local request carries the shared transport-neutral protocol hello and receives a negotiated protocol/capability welcome before work is processed. This is a compatibility boundary only; remote authentication is verified by ControlService over the Gateway-only local pipe. ControlService remains the source of truth for pairing approval, expiry, revocation, ownership, and capability grants. Its support snapshot includes a redacted paired-device list and excludes credentials, credential hashes, polling secrets, and private keys.

Administrator Gateway settings updates validate bind addresses, advertised DNS/IP hosts, and ports before saving so invalid endpoints cannot prevent Gateway startup.
Pairing QR creation also checks that the requested HTTPS origin matches an endpoint registered by the running Gateway.
ControlService reconciles the installer-owned Private, Domain, and Public Gateway firewall rules with the saved listener port and `AllowPublicNetworks` setting. Public is off by default; only an administrator may change the setting.

## Development

Local replay-protected mutations reserve their user/request ID and payload fingerprint before dispatch. Successful replies are retained for 24 hours; confirmed failures release their reservations. Pending/uncertain requests remain blocked as `OutcomeUnknown` across service restarts and are not evicted to make room. Capacity exhaustion rejects new reservations rather than losing an existing guarantee. Version-2 records add pending state; unversioned version-1 completed records remain readable, and atomic writes retain the prior ledger as backup. An unreadable/invalid/missing-with-backup local ledger blocks all state-changing client requests while read-only queries continue. Repair the authoritative ledger and restart ControlService; do not silently restore an older backup or discard history.

Remote shortcut execution uses the same machine lease and operation routing as local shortcuts. Asynchronous display-profile acceptance retains its lease until the matching terminal Agent status arrives. Idle heartbeats cannot clear an explicit reservation or a recovery requirement, and a reused Windows session ID cannot let another user's heartbeat update the old lease. Launcher/RPC failures return structured responses; ambiguous mutation replies retain their replay reservation and display recovery lease. Gateway requests validate both the envelope version and nested JSON before dispatch.

Decision answers arriving at or after expiry resolve the prompt using its existing default and reject the late answer, independently of the periodic expiry sweep. Atomic state replacement retries sharing/lock violations and Windows replacement contention up to three attempts, retaining atomic replacement and backup semantics. Persistent or unrelated failures still propagate.

```powershell
dotnet build .\DisplayMagician.ControlService\DisplayMagician.ControlService.csproj
dotnet test .\DisplayMagician.ControlService.Tests\DisplayMagician.ControlService.Tests.csproj
```

The service is installed and configured by the WiX package; do not manually register a development build as a production service. Build the complete installer through `build_displaymagician.ps1`.

Machine-owned state, audit records, and logs live under `C:\ProgramData\DisplayMagician\Machine\` in an installed environment. See the [architecture plan](../DISPLAYMAGICIAN_V4_CONTROL_SERVICE_PLAN.md) for IPC, security, and ownership rules.

Legacy imports validate source content before replacing a destination and do not re-import retired `.old` files during retries. Concurrent migrations on the service's runner serialize. An existing marker must be readable, use schema 1 and contain complete successful migration records; an invalid marker stops import and returns a repair error while preserving both source and destination data. Marker validation does not replay a completed migration or require retired source files to remain present.

For a user-selected Support ZIP, ControlService stages retained machine logs, the installer transaction log, the audit log, and an allowlisted machine configuration snapshot (including gateway and temporary diagnostic settings and their backups). It does not stage pairing sessions, replay records, gateway identities, or other secret-bearing machine state.

Operation-status subscriber notifications drain in commit order outside the status lock. Each subscriber receives its own snapshot; subscriber failures are logged without changing authoritative replies or preventing other subscribers from receiving the update. Event-hub subscriptions likewise receive independent deep snapshots. The status-store recovery and durability policy is described below.

OperationStatuses.json now uses schema 2, containing each status and its accepted delivery IDs. The store reads legacy status arrays; the first successful replacement backs up the prior file through AtomicFileStore and writes schema 2. Later writes retain the usual rolling .bak. Accepted IDs for retained operations prevent older queued retries from rolling progress backwards after service restart. Legacy records can seed only their existing last delivery ID; new deliveries are tracked thereafter. Invalid/unsupported history, null/duplicate records, inaccessible paths, and a missing primary with an existing backup disable rewrites until repair/restart and preserve the files. Operations continue with in-memory status/coordination and error logs. A transient write failure leaves dirty state for retry. Status publication/reconciliation acknowledges durability only after saving; unsaved terminal updates still complete machine coordination. Command replay protection and actual display/audio recovery safeguards remain separate.

Machine support collection reports individual missing, locked, unreadable or invalid sources as warnings and retains readable sources. Optional absent backups are expected; inaccessible retained backups are reported. Filesystem links are rejected during traversal, staging writes and cleanup. Unsafe/unwritable staging remains a failed export. Pairing snapshots use the explicit redacted allowlist with no raw-file fallback. Source copies permit rotation and are bounded by the opening length.

Temporary diagnostic Set/Release requests retain the previous in-memory lease when persistence fails. The existing shared machine logging lease/expiry policy remains separate from the saved per-user WinForms/UserAgent level and is pending further design review.
