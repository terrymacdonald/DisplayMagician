# REST P2 installed test plan

Run this on an elevated Windows host with Windows Sandbox enabled. Build the current Debug bundle, then launch the repository's Windows Sandbox debugging workflow. Record the Gateway, ControlService, UserAgent, and WinForms versions used. Use a test phone or HTTP client that verifies the pairing QR's TLS SPKI pin and sends the shared protocol hello; never disable certificate verification.

The automated preflight is `verify_rest_p2_routes.ps1`, followed by the Gateway, ControlService, and UserAgent test projects. The checks below exercise the installed HTTPS and UI path that those tests cannot cover.

1. **Bootstrap and protocol.** Read `/v1/identity` and `/v1/capabilities` without a bearer credential. Confirm the welcome header, request ID, host identity, TLS pin, and capabilities. Confirm a missing or incompatible hello returns the documented Problem Details response before route work.
2. **Local pairing.** Show a QR in WinForms, submit a phone-generated polling secret with a UUID v4 idempotency key, and approve in WinForms. Check `202`, the pairing `Location`, polling before and after approval, exact requested grants, and one-time credential delivery. Check that a second delivery returns `410`, and that a wrong polling secret cannot read status.
3. **Paired approval and devices.** Pair a second device through an already-paired approver. Confirm it receives the same grants it requested. Check `/v1/devices/current` works without `devices-read`; check device list and revoke grants, self-revocation, and `401` on the next request using a revoked credential.
4. **Saved resources.** List and read one display profile, audio profile, and shortcut. Confirm IDs, names, links, and optional artwork match the installed user's saved items. Check unknown IDs return `404` and a device without the relevant read grant receives `403`.
5. **Operations.** Start one display-profile application, audio-profile application, and shortcut run. Confirm each `202` returns a server-generated ID and matching `Location`. Poll `/v1/operations/{id}` until `isFinished` is true; confirm status, phase, and links. Cancel a running shortcut and verify its final state. Confirm cancelling a completed or uncancellable operation returns `409 operation-not-cancellable`.
6. **Decisions.** Trigger a recovery decision, read it from the operation and pending inbox, answer it from an authorised client, and check that the operation advances. A new-key second answer must return `409`; an identical original-key retry must replay the retained result.
7. **Retries and restart.** Repeat each mutation with its original method, URL, content type, body bytes, and key; confirm the retained response and no duplicate action. Reuse a key with different content and expect `409 idempotency-key-conflict`. Restart Gateway and ControlService and verify completed replay. Interrupt a reserved mutation before result storage and verify `409 idempotency-outcome-unknown`; use its operation `Location` or affected resource to reconcile before any new action.
8. **Isolation and boundaries.** Pair two Windows users and confirm each device sees only its owner's resources, operations, decisions, and devices. Check a missing grant returns `403`, an invalid credential returns `401`, and a temporarily unavailable ControlService returns retryable `503` without treating the credential as invalid.

Record the HTTP status, `errorCode`, response shape, and relevant request ID for each failure. Keep credentials, QR secrets, and polling secrets out of the test record. Mark P2 complete only after these installed checks pass or each remaining exception is recorded in the roadmap.
