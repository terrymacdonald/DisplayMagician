# DisplayMagician.UserAgent

This project is the per-user background executor that runs in the interactive Windows session. It receives authenticated commands through the Control Service and performs display and audio changes, shortcut lifecycle and restoration, process/game monitoring, game-library discovery, vendor/native display integration, per-user message storage/sync, and user notifications.

The Agent is the owner of interactive desktop work. It starts its command pipe and restores pending state before it reports itself ready to the Control Service. The service performs machine-wide coordination and routing, but must not take over these responsibilities.

The command pipe validates every envelope and compatibility hello before replay lookup, including repeated requests. Matching concurrent request IDs share one in-flight execution; a changed command or payload is rejected. Different commands remain concurrent so cancellation is not held behind the work being cancelled. Successful responses retain the existing 24-hour in-memory cache; failed/cancelled executions are removed when they finish. ControlService's durable replay ledger continues to protect uncertain mutations across disconnections and process restarts. Null message collections, invalid repository kinds and blank profile names return structured validation errors before changing data.

Persistent service connections finish registration before other requests can use them. Cancelled, timed-out or malformed exchanges discard that connection so a late reply cannot be mistaken for the next command's response. Reconnection continues without stopping an active shortcut. Successful replies must match the frame version, request and ControlService endpoint.

On graceful shutdown or startup failure, the Agent stops admitting work, cancels active operations and waits for their cleanup before closing its service connection. Accepted command handlers are drained, and a committed idle-stop request still takes effect if its response pipe disconnects. A command-listener failure reaches startup instead of leaving migration waiting indefinitely. Forced process termination still relies on the saved startup recovery record.

Shortcut completion and startup recovery attempt independent display, audio and volume restoration steps even if an earlier restore throws. Progress-publication failures do not prevent restoration. Failed audio/volume restoration or failure to clear the recovery record leaves recovery pending, and manual-run cleanup always releases its automatic-detection suspension.

For shortcuts with a saved window snapshot, UserAgent tracks windows of the main game/executable and Start Programs launched in that run, then restores their normal bounds, maximized position, and normal/minimized/maximized state after launch. For automatically detected games it attaches the exact newly detected process before starting helper programs, follows that process's descendants, and waits for that selected tree to close instead of older copies. It skips uncertain matches, missing displays, and runs whose display-profile application failed. When multiple launches use the same executable, it prefers the process tree owned by each launch. A placement that does not take effect is retried at most three times, with failed attempts logged. An active run can replace its entire snapshot through the shared service API; already-running Start Programs are excluded. Failed window inspection keeps the existing snapshot. Shortcut file version 8 adds optional maximized coordinates to version 7's stable Start Program IDs and window-placement fields. The Agent backs up and atomically migrates older shortcut files before use.

Automatic game detection compares the PID and start time of processes matching the configured game executable. It ignores processes present at detector startup, retains a newly detected process while another operation is busy, and passes that exact identity to ShortcutRunner. A game library without a usable `.exe` requires the shortcut's Monitor different executable path. Process identities remain in UserAgent memory and are never persisted.

Manual game launches also exclude existing process identities and select the newest observed matching root. The selected tree owns both window placement and shortcut completion, including descendants that survive a launcher. Descendants are discovered before exited parent identities are retired, with creation-time checks to exclude reused PIDs. Start/After Programs check full executable paths, and Stop Programs verify full paths and process identities before stopping anything.

Shortcut JSON uses `MonitorLaunchedExecutable` as its canonical monitoring flag. The Agent-owned migration normalizes the older `ProcessNameToMonitorUsesExecutable` and `MonitorExecutablePath` names. Existing canonical values take precedence, unrelated fields are retained, and the original file is backed up before replacement.

Shortcut schema 9 adds individual 0-999 second waits after successful Start/Stop Program actions, including UWP starts and the last action before launching the main target. The Agent publishes wait progress through shared operation status, and cancellation follows normal cleanup/restoration. Disabled entries, already-running starts, absent stop targets, and failed actions do not wait. Migration preserves existing delays and adds zero defaults; After Program delays are stored but not executed.

Process-tree callers retain distinct selection rules:

| Caller | Root selection and lifetime |
| --- | --- |
| Automatically detected game | The exact PID/start-time identity detected before helper programs run, plus descendants. |
| Manually launched game | Discover new matching identities, then select the newest observed root and its descendants. A library client such as Steam is not accepted as the game. |
| Executable / unpackaged application, launched executable selected | Register the actual launch handles and follow only their owned trees. Retained alternative-path text is ignored. |
| Executable / unpackaged application, alternative executable selected | Keep discovery open until a new matching alternative executable appears, including when started by a broker outside the launcher's tree; then select its newest root. |
| Start Program / direct StartAndCapture caller | Register its launch handles and restrict tracking and cleanup to those owned trees. Another helper or user launch of the same executable is excluded. |
| Legacy game-library status monitor | Retain startup discovery behavior; after an explicit tracking failure, status remains conservatively unknown/running rather than claiming the game exited. |

Native snapshots use a collection-time boundary to reject identities born after the snapshot began. When a parent's PID has been reused, child creation times distinguish surviving children of the original parent from children of its replacement. Ambiguous snapshot entries defer parent retirement until a fresh scan can verify the handover.

Failed, empty, incomplete, or unverifiable snapshots do not count as completed discovery. Retry attempts are separated by at least 250 ms and stop after three consecutive failures, with an explicit error log. Active shortcut lifecycle checks report tracking failure through the shared operation status and restore temporary settings, rather than reporting normal process completion. A successful retry clears transient snapshot uncertainty so window capture can resume. Cleanup refreshes the owned tree before selecting processes to stop.

Shortcut recovery record version 2 embeds the original display (including wallpaper) and audio configurations before temporary changes. Restoration uses these snapshots independently of the saved profile collections. Version 1 records continue to recover by their existing profile IDs without being rewritten: the original configuration cannot be reconstructed after a change has already occurred. Missing or unsupported recovery data remains in place and requires recovery rather than silently discarding it. Snapshot serialization excludes rendered icons and cache files.

Profile list responses include compact layout thumbnails. A client may request a labelled preview and multi-size desktop `.ico` for one selected profile or a preview for the current layout; the Agent renders these from its authoritative display and saved wallpaper configuration, falling back to the display colour when a saved wallpaper cannot be read. Compact thumbnails are used for list and game shortcut overlays. Shortcut-list icons prefer the user's saved composite image over an executable-derived fallback.

Successful direct display and audio profile edits return the saved profile ID and change action to ControlService. This lets the service publish precise saved-resource events after the Agent commits the edit. Bulk repository edits are compared by saved ID in ControlService.

Shortcut startup refreshes current display/audio state before deciding whether a profile is already active. A shortcut is successful only after its required restoration succeeds; incomplete restoration retains its recovery file and reports `RecoveryRequired`. Display/audio profile edits propagate write failures and roll back their in-memory changes. Icon deletion occurs after the profile collection is saved.

Direct audio, display, and shortcut execution share Agent admission checks. Active work prevents an idle stop and overlapping execution; once stopping is accepted, new operations are rejected. On a new Agent process, startup recovery resolves previously persisted active operations as interrupted failures. A Control Service reconnect preserves operations still executing in the same Agent process.

MessageSyncService owns message-index writes. Sync downloads are serialized, while final metadata commits merge the latest read/unread states under the same lock used for read-state edits. Downloads do not block a user from marking messages read or unread. Existing persisted schemas and transport contracts are unchanged.

Shortcut schema 10 adds the per-entry `StopAllInstances` boolean, defaulting to false for new and migrated entries. Stop Programs select the newest matching PID/start-time identity by full executable path unless the user opts into all instances. Repeated entries select the next newest remaining instance. Successful stops immediately retain one restart action per configured entry, even if another selected instance fails; a surviving instance does not suppress that restart. Cleanup runs in reverse action order, logs failures, releases process/monitor resources and continues with remaining entries. Expected helper preparation failures use the existing Continue/StopAndRestore decision flow.

Shell dispatch is distinguished from receiving a process handle: successfully handing work to an existing shell application does not cause an invalid PID read. Start-and-forget reports dispatch success; monitored launches still require their existing process-selection checks. Existing provider log argument contents remain unchanged by user choice.

Shortcut version checks run before legacy cleanup can modify invalid-version files. Unsupported newer versions are refused at startup, repository reads/commits and window-snapshot saves; originals and existing backups are preserved. Supported older versions are upgraded once, and current-version files are not rewritten just by loading. Missing/blank legacy markers remain supported.

Steam, Epic and GOG discovery distinguish a complete empty catalogue from an incomplete scan. Read/parse failures mark the provider incomplete even when other entries were readable. Existing catalogue publication rules remain: a failed refresh retains the previous complete combined/provider catalogues; a first scan publishes successful providers and excludes failed providers' partial results. Readable empty Epic installation lists/manifest directories and GOG support directories succeed so removed final titles can disappear on refresh. Missing/unreadable required metadata remains a failure.

Steam text discovery reuses the existing ValveKeyValue dependency for current/legacy library folder files and app manifests. It accepts valid whitespace, comments, escaped paths and line-ending variations, deduplicates folder paths without case sensitivity, and continues scanning other manifests/users after individual errors while returning an incomplete result. Ordinary catalogue reads still use the cache; this work does not add background rescans, change launch arguments/log contents or alter shortcut data.

Origin and Ubisoft discovery follow the same refresh policy: per-game metadata read/parse failures mark the provider incomplete while other records continue; a readable empty installation source succeeds and clears stale entries. Origin installer versions use invariant number parsing and reject invalid/mismatched structures. Legacy v2 manifests preserve the executable extension, match `.par` basenames literally and resolve relative paths within the game's installation. Download/uninstalled filters remain in place. Ubisoft recognises installed records through the existing product/install identifiers, reports their unreadable/empty configurations as incomplete, and preserves filtering of unrelated/non-launchable cache records.

Steam's app-info reader checks string-table offsets/counts and record lengths against the available bytes before allocating, requires null-terminated table strings and confines binary VDF to each declared record. App/package readers replace their published list/universe only after complete success, so repeat reads do not accumulate entries and failed reads retain the previous result. Owned streams close on failures as well as success; the package parser currently has no production callers. Supported binary signatures are unchanged. Fixture verification does not establish compatibility with the latest installed Steam client; that remains an explicit manual check.

Process identity/status verification no longer treats inspection failures as confirmed exits. Monitor status queries and synchronous ProcessExited checks retry at most three times with short backoff, log failures and report a tracking failure when uncertainty persists. Native descendant/retirement checks retain uncertain identities for the existing bounded snapshot retry. Launched-process registration retries identity reads up to three times with cancellation support and fails explicitly when a returned process cannot be verified as a new launch. Failed registration discards speculative unowned discoveries; helper cleanup and window sources require verified launch-tree membership. Existing newest-process selection and launcher/descendant lifetime rules remain in place.

Packaged Start Programs are scheduled for Close on finish only when activation ownership is proven: the PID was absent before activation, its start time is new and its AUMID matches. Existing/reused or uncertain instances remain running and the skip is logged. Activation remains usable without cleanup ownership. The native activation COM object is released in a finally block, and temporary process snapshots are fully disposed. This fixes the existing activation path without adding UWP process-tree/window-placement features or changing persisted schemas.

## Development

Message read-state changes and synchronization report index-write failures instead of reporting an unsaved change as successful. Process launch logs include the executable and process ID, with raw command arguments omitted from support logs.

```powershell
dotnet build .\DisplayMagician.UserAgent\DisplayMagician.UserAgent.csproj
dotnet test .\DisplayMagician.UserAgent.Tests\DisplayMagician.UserAgent.Tests.csproj
```

Run an Agent build only in an interactive Windows session. It needs the installed native/vendor dependencies and the Control Service connection to exercise real operations.
Windows shortcut creation and inspection use the registered `WScript.Shell` COM object at runtime, so `dotnet build` does not need to resolve a COM type library.

Configuration and recovery data are user scoped. Maintain backward-compatible JSON and explicit migrations when changing persisted models. See the [architecture plan](../DISPLAYMAGICIAN_V4_CONTROL_SERVICE_PLAN.md) for the Agent's ownership boundary.

Profile snapshot comparison, commit and cache installation run under the owning repository's lock, shared by runtime edits, saves and loads. Shortcut snapshots retain the ShortcutStore lock. Repository commits validate the document before atomic replacement, preserve unknown JSON fields and retain the previous file as `.bak`. A committed profile list remains available if a runtime save occurs before the next lazy reload. Save verification compares the complete saved text with the serialized input; serialization errors prevent replacement. Shortcut migrations use the same atomic writer, unique migration backup names and skip schemas newer than version 9 in both migration steps.

Profile rename, replacement-from-current and display-settings edits resolve a supplied profile reference to the current repository object by ID while holding the repository lock. A profile deleted by another client is rejected before editing or hardware capture. An older reference cannot overwrite unrelated fields from a newer snapshot; failed saves roll back the current definition.

Saved display-profile wallpaper copies live in the user's `Wallpaper` directory. On profile deletion or replacement, the Agent removes an old copy only after the profile snapshot has saved successfully, only when no profile still references it, and only when the file is directly inside that managed directory. Original wallpaper paths outside DisplayMagician storage are never deleted by this cleanup.

The user-selected Support ZIP includes current user configuration and retained logs, approved pre-v4 configuration backups, legacy/backup logs, and the Control Service's staged machine snapshot. Migration backups are limited to known configuration filenames; staging files, icons, wallpapers, and unrelated files are not collected. `support-manifest.json` records included entries, their collected byte lengths and collection warnings. Exports are closed and flushed in a sibling temporary file before replacing the selected ZIP; failed exports preserve the previous file. The destination and temporary archive are excluded from collection. Filesystem links (including linked ancestors) are skipped with warnings; unreadable folders do not prevent collecting readable siblings. Source-read interruptions are reported as partial entries, while archive-write failures fail the export.

Game launch and automatic detection resolve games using both the saved library and game ID. Explicit ListGames refresh requests rescan libraries; ordinary reads use the cache once loaded. Scans serialize and publish the combined catalogue after all providers finish. Failed later refreshes restore prior provider/combined lists. On the first scan, successful providers remain available and failed providers are logged with their partial entries excluded. Provider discovery remains interactive-session work and hardware/vendor-library validation is still required.

Operation-status enqueue, flush and reconciliation share an asynchronous delivery gate. Reconciliation drains pending updates first and runs only when the ordered acknowledgement prefix is complete, preserving UpdateId and phase order. Degraded storage delivery is described below. Startup interrupted-operation completion uses the same gate. Cancellation commands retain their independent operation-ID checks and do not wait on status delivery.

An invalid, unsupported or inaccessible status outbox is preserved with its backup, with rewrites disabled until repair/restart; new status tracking continues in memory. Ordinary write failures retain dirty state for retry. Local acknowledgement failures restore the pending prefix. Explicit service memory-only responses permit later ordered phases, including terminal status, to be delivered without discarding earlier unacknowledged updates; transport failures still pause the batch. This prevents reporting-storage faults from blocking machine coordination. Service-side schema-2 delivery history makes the retained retries harmless across restart. Deploy the updated ControlService and UserAgent together. In degraded mode, progress/history may be lost across a crash; command replay and actual shortcut recovery storage keep their existing safeguards.

The Agent follows ControlService's shared logging settings through its authenticated persistent pipe. A dedicated loop polls every two seconds and evaluates cached session expiry while a reply is pending, so transport delays do not hold an expired diagnostic level. Saved Trace through Fatal levels apply across restarts and running components. The previous independent per-user Settings reader is replaced by the shared baseline and renewable-session policy; see the ControlService README.


PrepareUserAgentForReset (104) is accepted only through the existing ControlService-authenticated command pipe. It prevents new work, cancels tracked operations, waits for completion/idle/restoration and requests shutdown only after recovery is clear. Failure/cancellation leaves the Agent available and recovery data intact. Startup exits while the installation-maintenance gate is present. No general reset/storage deletion or expanded SessionLauncher permissions are added to UserAgent.


The explicit --acquire-display-control startup option acquires only after migration, pending restoration and the ready-registration response. This preserves startup recovery before new work; ordinary startup/reconnect wire formats are unchanged.

Display operations publish additive `DisplayResults` through the shared operation status contracts. Required topology/grouping, resolution, rotation and positioning failures use the existing Continue/StopAndRestore decision and disable window placement for that run. HDR, refresh-rate, scaling and optional vendor-setting failures are warnings: execution and placement continue. Display restoration failures are reported as warnings and do not alone retain recovery; audio/volume restoration and recovery-file clearing still run, with their existing failure handling. Native stage, component, display identity and available error codes survive status delivery, persistence and reconnection for authorised clients and support logs. Existing vendor application order, wake-up steps, delays and retries are retained.

The Windows topology-only recovery attempt uses a temporary path copy with invalid mode indexes and no mode array, preserving path order and legacy/virtual clone membership. It retains virtual-mode awareness when omitting dynamic refresh awareness. Native capture and scaling run in a thread DPI context that restores the caller's exact previous context on exit; the display library no longer changes process-wide DPI defaults. HDR comparisons consume each equivalent entry once while retaining display-ID tolerance. After successful Windows display queries, buffers are shortened to the returned path/mode counts before processing and capture. Every entry within that range stays at its original index, including zero-valued clone entries; allocation/retry logic is unchanged. New snapshots store those exact ranges without adding capacity metadata or changing the profile schema. Full video-only integration validation is deferred to Terry's VideoInfo application.

NVIDIA Surround and DRS result handling is shared with regression tests through the partial NVIDIALibrary.Configuration.cs file. Surround creation/removal checks wrapper success and uses the existing refreshed cache to decide whether work is needed, retaining the existing preparatory 1x1 step, legacy disable fallback and delays. Optional overrides skip stale comparisons after a failed refresh; DRS capture failures omit the snapshot, and known incomplete saved snapshots cannot trigger writes or default resets. Driver-setting write/reset/save failures are warnings. No profile schema or native wrapper binary changes are required. Copy both NVIDIALibrary.cs and NVIDIALibrary.Configuration.cs when testing these changes in VideoInfo.

AMD optional scalar/toggle restoration requires support recorded in the saved snapshot as well as current driver support. Active legacy SLS maps are selected per adapter while IsEyefinity/IsSlsEnabled remain aggregate contains-any flags; empty required legacy map snapshots fail explicitly. The Windows display-change path remains MainForm.WndProc -> tray profile refresh -> ControlService ListProfiles -> UserAgent profile capture/cache update. Operations retain their existing explicit capture and required post-apply verification.

AMD gamma/gamut restoration sends the saved portable values to ADLXDisplay.TryApplyGamma/TryApplyGamut in the shipped ADLXWrapper. These additive methods differ from the existing Reapply methods, which read current hardware state. Deploy this Agent with its updated DLL/XML from the approved ADLXWrapper checkout; existing saved profiles and schemas are unchanged. Unsupported/native-write failures retain the optional-setting warning policy.
